# 《权谋之庭》原创文风体系设计

**日期：** 2026-08-04

**状态：** 已完成口头设计确认，等待书面审阅

**范围：** 仅限《权谋之庭》；成熟后是否提炼为跨项目通用文风，另行设计

## 一、背景

全局 `writing-game-copy` 已停用并移出自动发现目录。新体系不再模仿外部游戏，也不把模型自行判断为“优秀”的旧文本当作范文。

项目已有 `STYLE.md` 和 `FORBIDDEN_PHRASES.md`。它们积累了有用的历史经验，但规则密度过高时会反过来塑造新的模板腔。新体系因此改用“用户批准的项目原文”作为唯一正例来源，把规则放在样本之后，而不是样本之前。

## 二、目标

1. 建立只属于《权谋之庭》的文风库。
2. 让文风来自用户逐段批准的文本，而不是外部模仿、自动评分或模型自评。
3. 覆盖权力谈判、谜案揭露、私人感情、治理民生、失败妥协和结局尾声六类核心叙事功能。
4. 在未来写作时只读取少量最相关的正例，避免整本手册压过当前人物和场景。
5. 用盲测验证文风库是否真的提高命中率，再决定是否判定成熟。

## 三、非目标

- 本设计不直接重写现有剧情。
- 本设计不追溯收录任何旧文本；旧文本只能成为待审候选，不能自动转为正例。
- 本设计不创建新的全局写作 skill。
- 本设计不提炼跨项目通用文风。
- 本设计不让 `scan_ai_smell.py` 或其他自动扫描器裁决文本质量。
- 本设计不新增美术、音乐、音效、动画或 UI 资产。

## 四、已比较的方案

### 方案 A：三稿短片盲选（采用）

针对同一份场景事实卡，独立生成三篇结构不同的短稿。用户选择、拼接、修改或全部否决。只有最终明确批准的文本可以入库。

优点是能减少首稿锚定，并更快暴露用户真正偏好的节奏、叙述距离和人物声口。代价是前期每轮需要阅读三篇短稿。

### 方案 B：单稿逐句打磨（不采用）

效率较高，但最终文本容易保留第一份 AI 草稿的结构，只是把句子修顺。

### 方案 C：边修游戏边积累（成形期采用）

能同步改善正式内容，但早期会把文风判断与 canon、变量承接、分支逻辑混在一起。待首批样本形成后，再用这一方式扩充文风库。

## 五、核心原则

### 5.1 正例的唯一来源

- 只有用户今后逐段明确批准的最终文本才能成为正例。
- 模型、扫描器、现有项目文本和其他作者都没有自动准入资格。
- 用户只批准部分句子时，只保存这些句子，不补写或推断缺失上下文。
- 已批准文本被用户撤回后，立即从活动索引和活动文风库移除；Git 历史保留恢复能力。

### 5.2 反例不留原文

- 被否决的候选稿不写入项目文件。
- 只记录用户亲自指出的失败原因。
- 优先保留用户原话；需要压缩或改述时，必须再次得到用户确认。
- 模型自行发现的问题可以在当前轮用于改稿，但不能擅自进入长期失败原因清单。

### 5.3 事实约束与文风分离

候选稿可以读取：

- `CANON.md`；
- 当前场景的连续上下文；
- 当前分支变量与人物知情范围；
- 最多三个相关的已批准正例。

候选稿不得读取：

- 归档后的旧 `STYLE.md`；
- 归档后的旧 `FORBIDDEN_PHRASES.md`；
- 任何外部游戏语料；
- 被否决稿全文；
- 未经用户批准的模型文风总结。

## 六、采样循环

每轮只处理一个 250～450 字的小场景。

1. **建立事实卡。** 固定人物、地点、已发生事件、人物已知信息、本段必须完成的叙事功能和不可改变的分支结果。事实卡不包含文风指导。
2. **独立起草。** 三份候选稿使用同一事实卡，彼此不可见，结构必须有真实差异，不能只做同义替换。优先交给三个隔离的子代理；如果运行环境无法隔离候选稿，本轮不得计作文风校准样本，必须先向用户说明。
3. **用户选择。** 用户可以选一稿、拼接几句、亲自修改或全部否决。
4. **清稿确认。** 根据用户选择整理出一份完整终稿，单独展示并询问是否收录。
5. **明确入库。** 展示终稿后，必须单独询问“是否收录为 COS-xxx？”只有“收录”“确认”，或在该问题下直接回答“可以”，才写入 `approved/`。“继续”“差不多”“先这样”等含糊回应不触发收录。
6. **处理否决。** 候选稿立即丢弃；若用户指出失败原因，只把该原因追加到失败原因清单。

首批六轮依次覆盖以下固定枚举：

1. `power_bargain`：权力谈判；
2. `mystery_reveal`：谜案揭露；
3. `private_relationship`：私人感情；
4. `governance_livelihood`：治理与民生；
5. `failure_compromise`：失败或妥协；
6. `ending_epilogue`：结局尾声。

首批六轮只用于校准，不直接改动正式 `.rpy` 文本。进入成形期后，转为“边修正式文本、边收录已批准片段”。

## 七、文件结构

```text
docs/writing-style/
├─ INDEX.md
├─ scene-card-template.md
├─ failure-reasons.md
├─ validation-log.md
└─ approved/
   ├─ COS-001-权力谈判.md
   └─ ...

docs/archive/writing-style-legacy/
├─ STYLE.md
└─ FORBIDDEN_PHRASES.md
```

### 7.1 `INDEX.md`

负责说明调用边界、展示成熟阶段，并按样本编号、场景类型、角色、文本形态和批准日期建立索引。它不包含未经批准的文风总结。

### 7.2 `scene-card-template.md`

只定义每轮事实卡的字段。具体事实卡属于当轮临时材料，不进入文风语料库。

### 7.3 `approved/`

每个文件只包含必要元数据和被用户批准的文本。建议字段如下：

```yaml
id: COS-001
status: approved
scene_type: power_bargain
characters: [角色名]
text_mode: dialogue
sample_kind: full
approved_on: 2026-08-04
```

正文只能放已批准内容。不得加入模型撰写的赏析、风格归纳或未获批准的衔接句。

`sample_kind` 只有两种值：

- `full`：用户明确批准整份清稿，且文本完成了事实卡要求的叙事节拍；计入成熟度。
- `fragment`：用户只批准其中若干句；允许进入正例库供检索，但不计入成熟度。

### 7.4 `failure-reasons.md`

只保存用户指出并确认的失败原因、日期和适用场景标签，不保存被否决原文。文件采用固定单行表格：`日期 | 场景类型 | 用户确认的失败原因`。允许保留用户点名的短语，不允许粘贴整篇候选稿。

### 7.5 `validation-log.md`

只记录盲测轮次、场景类型、随机位置、被选方法和是否出现新失败类型，不保存落选稿。

### 7.6 项目入口

- 新增根目录 `AGENTS.md`，让 Codex 在涉及游戏文案时读取 `CANON.md`、当前上下文和 `docs/writing-style/INDEX.md`，并继续以 `CLAUDE.md` 中与文风无关的开发、演出和测试规则作为项目技术门禁。
- 修改 `CLAUDE.md` 的写作入口，使其他开发代理遵循同一来源。
- 旧 `STYLE.md` 和 `FORBIDDEN_PHRASES.md` 移入历史归档，不删除。
- 同步修改 `CANON.md` 开头的旧文风文件引用、`Tools/scan_ai_smell.py` 的提示文字，以及 `Tools/test_release_contract.py` 中针对两个根目录文件的包排除契约，避免迁移后出现失效路径或假失败。
- 历史设计、提交记录和旧计划中的旧路径保持原样，避免篡改历史证据；只有活动入口不得继续依赖它们。

## 八、正例检索规则

每次写正式文案时，最多加载三个正例：

1. 优先同角色；
2. 其次同场景类型；
3. 再次匹配对白或旁白形态；
4. 若仍超过三个，优先使用最近批准的样本。

没有合适样本时，不得拿不相关范文硬套。该段按事实自由起稿，并明确标记为“尚未校准”，继续走三稿盲选流程。

## 九、成熟阶段

### 9.1 萌芽期：0～5 段

- 始终采用三稿盲选。
- 不生成长期文风总结。
- 不修改正式剧情。

### 9.2 成形期：6～11 段

- 六类核心场景至少各有一段正例。
- 可以根据正例提出共同特征，但每条特征也必须由用户明确批准后才能进入活动指导。
- 开始在正式剧情中按小段修订并继续收录。

### 9.3 成熟期：至少 12 段

- 六类核心场景各有至少两段正例。
- 进行三轮陌生场景盲测：每轮一稿读取文风库、两稿不读取，随机打乱后交给用户选择。
- 读取文风库的稿件至少两次被选为主要底稿。
- 用户混合多稿却没有指定主要底稿时，该轮不计入成熟度成绩，重新安排一轮陌生场景。
- 读取文风库的稿件不能产生新的、被用户确认写入 `failure-reasons.md` 的失败原因。

满足全部条件后，才把《权谋之庭》文风标记为成熟。是否从中提炼跨项目通用部分，需要用户另行批准并建立新设计。

## 十、误收录与异常处理

- **含糊认可：** 不收录，重新展示终稿并询问是否收录。
- **部分认可：** 只保存明确圈定的部分。
- **三稿全拒：** 删除全部候选，记录用户指出的原因，重新检查事实卡后开始新一轮。
- **用户改写：** 以用户改写后的终稿为候选，再次确认后入库。
- **后来撤回：** 从活动目录和索引移除，不转为反例；Git 历史保留。
- **无匹配范文：** 不扩大检索范围，不调用外部语料，回到未校准流程。
- **canon 与文风冲突：** canon 和分支事实优先，不能为了贴近样本制造剧情错误。

## 十一、验证

计划新增 `Tools/validate_writing_style.py`，只做结构验证：

- 正例编号唯一；
- 元数据完整且 `status` 必须是 `approved`；
- `scene_type` 必须属于六个固定枚举，`sample_kind` 必须是 `full` 或 `fragment`；
- `INDEX.md` 链接存在；
- 活动入口不配置旧文风文件或外部语料的可读取路径；
- 失败原因文件符合固定单行表格结构，不包含整篇候选稿；
- 六类场景只统计 `sample_kind: full`，计数必须与成熟阶段一致。

自动工具不得给文本打文学质量分。文风质量只由用户盲选与明确批准验证。

正式 `.rpy` 文本开始改动后，仍须运行项目原有的 canon、立绘、Ren'Py lint 和相关回归测试。`scan_ai_smell.py` 可以保留为历史诊断工具，但不再是文风通过门槛。

## 十二、完成标准

第一阶段实施完成时应满足：

- 项目内文风目录和空白索引建立完成；
- 旧文风文件已可恢复地归档；
- `AGENTS.md` 与 `CLAUDE.md` 指向新入口；
- 结构验证脚本通过；
- 活动写作入口不再引用外部范文或旧禁令手册；
- 工作树中的改动已测试并提交；
- 第一张事实卡准备完成，但在用户看到三稿并明确批准前，正例库保持为空。

## 十三、资源结论

本体系只涉及项目说明文件、索引和验证脚本，不改变游戏演出。无需新增美术、音乐、音效、动画或 UI 资产，也不会增加发布包体。
